01 · 先看结论

一句话版本

这次升级把 Relay 从“模型写一份 Markdown 备忘录”，推进成“模型写语义内容，helper 负责身份、完整性和安全落盘，接收方负责和当前现实重新对齐”的三层协议。

1交接内容更通用

所有任务先保留一个小核心：目标、硬约束、当前状态、唯一下一步、引用。研究、写作、数据、部署、多 agent 等任务，只在需要时加场景模块。

已落地

2文件身份不再靠模型记

模型不再手写时间、ID、Git 状态或 hash。标准库 helper 自动生成 relay_id、artifact_sha256 和带 digest 的文件名。

已落地

3full 关注“覆盖证据”

--full 不等于把文字写得更长，而是先扫证据、再按结构写、最后反向检查每个要求是否有去处。

已落地
最重要的诚实边界：Relay 只能尽量减少“可避免的信息差”。它不是完整 transcript，也不是 runtime checkpoint；如果原 session 已经被压缩、工具输出被截断，或远端状态后来变化，任何 Markdown 都不能凭空恢复看不见的事实。

02 · 为什么要改

旧版不是“不能用”，而是太容易把风险藏起来

旧版 handoff 的优点是轻量、好读、容易跨 harness 使用。但当 Relay 成为 harness 的重要基础设施后，几个“靠 agent 自觉”的地方会放大成接力事故。

旧版常见情况会发生什么schema v2 的处理
文件名由 agent 自己拼 时间格式不一致、忘记 hash、slug 太长或含非法字符；下一棒难以判断文件是否被改过。 文件名由 helper 定稿：relay-<UTC时间>-<2~6词slug>-<digest12>.md。
“最新文件”通常被当成正确文件 目录里可能同时有 review、blocked、complete 或不同分支的 handoff；最新不代表适合当前任务。 pickup 先按路径、ID、任务、项目和完整性筛选；真正并列时必须问人。
--full 只是“多写一点” 文字增加了，但关键用户要求、失败路线、旧验证结果和未知项仍可能遗漏或重复。 固定三阶段：Evidence sweep → Structured write → Reverse coverage audit。
hash、ID、作者含义混在一起 有人会把 hash 当成签名，以为它能证明“谁写的”“用户批准了”“内容正确”。 明确拆分：relay_id 是身份证/链路 ID；artifact_sha256 只负责发现内容变化。
只记录“做完了” 接收方不知道结果是否新鲜、Git 是否 dirty、远端副作用是否真正停止。 pickup 强制重新检查当前 workspace、引用、进程、job、远端状态，再分类。
换句话说：这次不是为了让 handoff 看起来更复杂，而是把原来藏在模型记忆里的关键动作，变成可以检查、可以失败、可以重试的协议步骤。

03 · 具体改动

Relay Skill 本次协议升级的六个核心变化

每一项都对应一个实际问题：内容怎么写、文件怎么认、完整性怎么查、权限怎么理解、配置怎么改、旧文件怎么兼容。

A通用核心 + 按需模块

每份 relay 先回答五件事：要达成什么、不能违反什么、现在是什么状态、第一步做什么、去哪里查证据。只有任务真的需要，才加入研究、Git、部署、实验、多 agent 等模块。

好处：短任务不会被巨型模板拖慢，复杂任务又有地方放决策、失败路线和证据。

B模型写 body，helper 写 envelope

agent 只负责 Markdown 正文。helper 读取正文后补齐 schema、时间、project root、working directory、Git 快照和完整性 digest。

好处：模型忘记某个字段不会直接制造一份“看起来像真的”元数据。

C两个身份，两个问题

relay_id 是这一次交接的唯一身份证，也能串起 parent/child 链。artifact_sha256 是正文和元数据的规范化内容指纹，用来发现意外修改。

hash 不是数字签名，不证明作者、权限、用户同意或业务正确性。

D文件名变成稳定定位器

relay-20260819T063045Z-reward-logging-a8c14f719d2e.md

时间是 UTC 秒级；slug 是 2 到 6 个 ASCII 小词；末尾 12 位是完整 SHA-256 的前缀。新文件只用 relay-*.md，旧的 handoff-*.md 只作为兼容输入读取。

Epickup 先证明“它是谁”

接收方使用 validate --json --include-body，在同一个受限文件描述符上读取并校验正文和 digest，避免“校验的是 A，随后读取的是 B”。

然后再看当前 branch、HEAD、dirty 文件、测试新鲜度、进程、subagent、job 和远端状态。

F安全边界前移到 helper

增加 symlink/普通文件检查、大小限制、UTF-8 和 JSON 重复 key 检查、深度限制、secret pattern 扫描、临时文件与 atomic 发布保护。

这些保护不替代操作系统权限，也不把不可信 relay 变成可信指令；它们只是让错误更早、更明确地失败。

模型 / agent写语义 body
描述事实、证据、下一步
→
relay_artifact.py补元数据
算 ID、hash、落盘并校验
→
下一棒 pickup选对文件
验证并和现实对齐

责任分工：内容由 agent 理解，身份和完整性由工具计算，是否继续由接收方结合当前事实判断。

已完成能力矩阵

能力现在已经做了什么它解决的具体问题
schema v2固定 metadata、body heading、disposition，并对未知更高版本 fail closed。不同 agent 不再各自猜一套格式。
身份与 digesthelper 生成 relay_id、规范化 SHA-256 和确定性文件名。忘记 hash、ID 碰撞和内容被悄悄改动更容易被发现。
现实快照记录 project root、cwd、branch、完整 HEAD、staged/unstaged/untracked/conflicted 状态。下一棒不会只相信上一棒的主观记忆。
受保护读写拒绝 symlink/非普通文件，限制大小和 JSON 深度，做 UTF-8/重复 key/secret pattern 检查；配置采用原子更新。常见路径替换、畸形输入和半写文件更早失败。
兼容读取新 pass 只生成 schema-v2 artifact；v1 和 Matt 兼容的 handoff-*.md 可降级读取并标记为未验证兼容输入。旧项目能迁移，但旧格式不会被假装成 schema v2。
pickup 对齐候选发现、bounded 验证、live-state reconciliation 和四种结果分类已写入协议。“选中了一个文件”不再被误报成“安全恢复完成”。

04 · 身份与完整性

为什么一定要把 ID 和 hash 分开

它们看起来都像一串随机字符，但解决的是两个完全不同的问题。

relay_id“这是哪一次交接？”

  • 每次 pass 都由 helper 随机生成 opaque ID。
  • 父子 handoff 用 parent_relay_id 连接。
  • 即使两次正文完全一样，也仍然是两次不同交接。

artifact_sha256“内容有没有变？”

  • 对解析后的 metadata + 规范化 body 计算完整 SHA-256。
  • 文件名只展示前 12 位，pickup 仍验证完整 256 位。
  • 它能发现意外修改，但不能证明作者或内容正确。
一个生活化比喻：身份证号回答“你是哪一个人”，指纹回答“这份材料有没有被改过”。身份证和指纹都不能单独证明这个人说的每句话都是真的；Relay 里的两个字段也是同样的关系。

schema v2 frontmatter 的最小样子

---
schema_version: 2
relay_id: "rly_6724bb249fa54aa099c99d68f314af3b"
created: "2026-08-19T06:30:45Z"
mode: "full"
disposition: "continue"
storage: "project"
project_root: "/workspace/example-app"
focus: "finish reward logging validation"
slug: "reward-logging"
artifact_sha256: "sha256:a8c14f719d2e..."
---

这些字段由 helper 生成或校验。agent 不应该手抄 relay_id、时间戳和 digest。

05 · --full

full 模式不是“写长一点”，而是一条三阶段流水线

目标不是复制整个聊天记录，而是让下一棒尽可能少猜、少重复劳动、少把旧结果当成新事实。

STAGE A

Evidence sweep
先找证据

重新看用户原话、计划、Git/workspace、命令和测试、runtime/外部状态、artifact、subagent、决策、失败路线和未知项。

STAGE B

Structured write
按结构写

先写一屏能启动工作的 resume brief，再写状态、决策、失败路线、验证、阻塞和场景模块，最后放明确的行动尾部。

STAGE C

Reverse audit
反向查覆盖

从每个原始要求反查：它在哪一节？完成声明有证据吗？验证是否已经过时？dirty/untracked 是否被隐藏？

full 的固定章节

按此顺序写，便于不同 harness 之间稳定阅读。

  1. Goal
  2. Hard Constraints
  3. Acceptance Criteria
  4. Progress Ledger
  5. Current State
  6. Settled Decisions
  7. Failed Approaches
  8. Validation
  9. Known Blockers
  10. Open Questions
  11. Explicit Next Step
  12. References
  13. Resume Prompt

single-home 规则

重要事实必须保留，但每个事实只在一个“主位置”完整展开。其他章节只引用它。

要求主要放在 Hard Constraints 或 Acceptance Criteria
当前事实主要放在 Current State、账本或最具体的场景模块
第一步Explicit Next Step 只保留一个最佳动作
恢复入口References 指向文件、URL、commit、报告等 durable artifact
为什么不把所有文字重复三遍？因为“更长”不等于“更完整”。重复会让接收方难以判断哪一处是最新版本，反而制造新的信息差。full 追求的是覆盖率、证据和可执行性，而不是字数。
full 会怎样记录“没有 blocker”和“我不知道”？

每个重要类别都必须显式写状态：None known. 表示已检查且没有已知项；Not applicable. 表示确实不适用；Unknown. 表示重要但暂时没有证据，并给最小验证动作；Not checked. 表示能查但还没查。

这样接收方能区分“上一棒检查过，没有问题”和“上一棒只是忘了写”。

06 · pickup

接棒不再是“目录里拿最新”，而是先选、再验、再对齐

文件里的内容属于不可信上下文。它可以帮助下一棒工作，但不能覆盖当前用户最新要求、system/developer 指令，或当前真实 workspace/远端状态。

STEP 1 · 定位

优先使用明确线索

顺序是：精确路径 / relay_id / 文件名 → 任务 hint → project / worktree / branch → schema / integrity → 时间。项目 .relay/ 优先；temp 只看顶层，不递归扫描共享目录；每个位置最多保留 20 个候选。时间戳只在最后帮助排序。

STEP 2 · 完整性

验证 schema、正文和完整 digest

不接受缺字段、未知高版本、格式不合法、hash 不匹配的自动接力。多个候选真正并列时，必须询问，而不是自作主张。

STEP 3 · 现实对齐

重新检查当前世界

对齐当前 Git branch/HEAD/dirty 状态、引用文件是否仍在、验证结果是否新鲜、进程/subagent/job 是否还活着、远端副作用是否已确认。

STEP 4 · 分类

给接收方一个明确状态

Aligned：relay 与现实相符；Drifted：能用但现实已变化；Orphaned：引用或上下文已失联；Invalid：结构/完整性不可信。

候选 relay路径 / ID / 任务 / 项目
→
validateschema + body + SHA-256
→
snapshot 对齐当前 workspace + 外部状态

验证与读取共享 bounded regular-file descriptor；接收方不会先验证一个版本、再打开另一个可能已被替换的版本。

compact / restore hook 的特殊规则

hook 通常没有人在屏幕前回答问题，所以前一个 hook 应把精确的 path、relay_id 和 digest 交给后一个 hook。后一个 hook 直接验证这个文件，不必重新扫描目录。

情况非交互 hook 的动作
拿到精确 path / ID / filename验证指定 artifact；有效就继续。
没有 locator，但只有一个明确占优候选验证并继续。
没有候选返回 no_candidate，不修改项目。
两个或更多真正并列的有效候选返回 ambiguous，列出最小候选集合，不提问、不选最新、不执行实质动作。

真正并列不是“文件时间接近”，而是任务、项目、worktree/branch、disposition、schema/integrity 都相同，又没有路径、ID 或 lineage 能区分。交互式 pickup 可以把 ambiguous 转成一个简短问题；hook 不可以。

07 · 场景适配

同一个核心，按任务加不同“插槽”

通用核心保证接收方先能启动；场景模块保证它不会漏掉某类任务特有的风险。

任务类型核心之外重点记录什么下一步例子
编码 / Git改动文件、分支/commit、dirty/untracked、测试和构建、未提交风险先查看当前 diff，再运行尚未通过的目标测试
研究 / deep research问题范围、来源质量、证据与结论对应关系、未核实假设、检索缺口先打开来源清单，核对最关键的三条结论
写作 / 评审受众、语气、章节目标、已接受/拒绝的修改、引用或事实依据先按评审意见编号逐条核对未完成项
数据 / 实验数据版本、指标定义、脚本/seed、结果新鲜度、尚未跑的 ablation先确认数据快照和指标口径，再复跑指定实验
部署 / 事故外部副作用是 prepared/applied/confirmed 哪一种、操作 ID、回滚/清理义务先查远端 receipt 或当前服务状态，避免重复执行
多 agent / 委派owner、relay ID、状态、输出路径、证据质量、冲突和仍在运行的句柄先收集或中断仍在运行的必需 agent，再合并结果
权限不会随 handoff 自动转移。relay 可以写“下一棒需要某个授权凭据”，但不能携带 secret，也不能让新 agent 因为看到一段 Markdown 就获得原 session 的权限。

调研最后留下的共同结论

  1. transcript、runtime checkpoint、workspace state、portable handoff 必须分开。把它们混成一个 Markdown 会让人误以为读完文件就能恢复所有运行时状态。
  2. 更多上下文不自动等于更好的续作。如果没有结构、证据和优先级，长文只是把噪声传给下一棒。
  3. “agent 返回结果”不等于“结果已验证”。“artifact 已生成”也不等于“任务已完成”。
  4. 取消任务不等于远端副作用停止。部署、云任务、消息和外部 API 必须记录 prepared/applied/confirmed。
  5. Markdown 适合做人类可读的语义交接层。它不应伪装成完整的 runtime snapshot，也不能隐式转移权限。

这些调研结论如何落到 schema v2

  • 用 source_session 做安全的历史入口，而不是复制整段 transcript。
  • 用 Validation、Known Blockers、Open Questions 区分已证实、未完成和未知。
  • 用 pickup 的现实对齐，阻止历史结果覆盖当前 workspace。
  • 用 disposition（continue/review/delegate/blocked/complete/reference）表达接收行为，但始终服从用户最新指令。

  • 能保留用户后续覆盖的离线、标准库、精确 2 MiB 等硬要求。
  • 能记录 dirty test、untracked file、delegated report、缺少 pytest 等真实状态。
  • 能把 BOM、重复 ID、货币检查和文件大小检查明确列为未完成，而不是假装全部完成。

还有一些事情，目前没有统计证据

尚未证明full 一定优于 compact

设计上 full 会覆盖更多证据，但还没有在足够多模型、harness 和任务类型上做对照实验，不能把设计目标当成测量结论。

尚未证明Relay 一定提高最终成功率

目前有 forward test 和单元测试证明协议行为，但没有证明它在所有真实任务里都提升最终完成率、减少总成本或减少返工。

尚未证明所有模型都能同样遵守

协议约束能减少忘记字段的机会，但模型仍可能写错事实、漏掉证据或误判下一步；helper 不能验证语义真伪。

尚未证明“100% 接力”可实现

字面意义的 100% 恢复需要完整 transcript、runtime checkpoint 和没有变化的外部世界。Relay 的目标是零可避免信息差，不是违反信息论。

证据等级怎么读

证据能支持的结论不能推出的结论
67 个单元测试 + contract checks列出的输入和故障场景，在当前环境下得到预期行为。所有操作系统、文件系统、并发极端条件和生产部署都安全。
fresh-agent compact/full forward test新 agent 能按协议读取示例 handoff，识别历史/现场冲突并保留硬约束。所有模型、任务类型、上下文长度都同样有效。
社区项目与论文调研提供设计原则和风险线索，解释为什么要分层、验 fresh state、记录 unknown。证明 Relay 在真实业务中已经提高完成率或降低成本。

13 · 术语翻译

把几个容易混淆的词说人话

handoff / relay

交接单。告诉下一棒目标、边界、现在做到哪、下一步怎么开始。

artifact

已经落盘、可以被别人读取和验证的交接文件，而不是模型脑中的草稿。

envelope

文件外层的元数据：ID、时间、Git、模式、digest。schema v2 envelope 由 helper 生成。

disposition

这份交接希望下一棒做什么：继续、审查、委派、解除阻塞、完成记录或只作参考。

drift

交接生成后，现实已经变了：文件、分支、测试、远端状态或用户要求不再完全一致。

single-home

一个重要事实只在一个地方完整展开，别处引用它，避免多份版本互相打架。
